## 1. 目标与非目标

### 目标

1. 落地 PRD §5.3 的秒杀链路：预热 → Lua 原子扣减 → Kafka 削峰 → 异步落库 → 超时回补 → 对账；
2. 产出可验证的并发结论：**10000 并发抢 100 件**，Redis 余量归零、DB 订单数 = 100、唯一索引零冲突；
3. 产出压测报告：秒杀热路径 QPS/P99、商品列表 P99、下单 P99；
4. 复用既有模式（Lua 原子、幂等索引、outbox、对账），不新造机制。

### 非目标

- 不做分布式锁、不做库存分片、不做多机房；
- 不接入真实支付（沿用 mock provider）；
- 不做秒杀活动的定时自动上下线（运营手动启停，见 §5.1）；
- 不改动 billing 计费内核。

### 反目标（即使功能跑通也算失败）

- 任何形式的超卖（Redis 余量为负、DB 订单数 > total_stock）；
- 抢购热路径上有同步 MySQL 写；
- 回补不幂等（同一订单超时回补两次，库存虚增）；
- 靠"压测时把并发调小"来通过验收。

## 2. 服务边界与命名

### 2.1 命名裁定：`services/mall-seckill`

PRD 原文写 `services/seckill`，但仓库有 [importguard](../pkg/importguard/doc.go) 边界门禁，规则 1 以 `services/mall-*` 前缀识别商城域。若沿用 `seckill` 名字，该服务不在商城域规则覆盖内，需要改门禁代码。

**裁定：改名 `services/mall-seckill`。** 理由：

- 零门禁改动——`isMallTree()` 的 `services/mall-` 前缀自动覆盖；
- 语义正确——它本来就是商城域服务，和 mall-bff / mall-goods / mall-order 同级；
- 部署名、容器名、proto 包名统一。

需要同步更新的引用：PRD §5.3/§10.1/§13、README 服务目录表、compose 服务名、`scripts/smoke-r4.sh`。

### 2.2 部署单元

| 进程 | 职责 | 端口 |
|---|---|---|
| `mall-seckill` | 抢购 API（Lua 扣减 + 写 Kafka）、活动查询、凭证查询 | 9113 gRPC / 9114 HTTP 健康口 |
| `mall-seckill-consumer` | 消费 `seckill.orders` → 落库建单 | 9115 HTTP（/healthz /status /metrics） |

端口 9113 由 PRD §3 分配；9114/9115 为本设计新增，需同步补进 PRD 端口表。

**消费者必须独立进程。** 决定性理由来自验收标准：

> 对账 job：人为造滞留（**停消费者**）→ 差异记录 + 保留待核查

若消费者与 API 同进程，"停消费者"就同时停掉抢购入口，造不出"有订单在途、无消费者处理"的滞留场景。这也与仓库既有先例一致——billing 的 `cmd/event-consumer` 就是独立进程。

业界对照：`qiurunze123/miaosha` 把 `MQReceiver` 放在 web 服务内，因为它是学习项目、不追求故障隔离；生产形态与 `system-design-primer` 的 worker 分层建议一致，即消费端独立、可单独扩缩。

### 2.3 服务间依赖

```
mall-bff ──gRPC──> mall-seckill ──Kafka──> mall-seckill-consumer ──SQL──> market 库
                        │                          │
                        └──gRPC──> mall-goods      └──gRPC──> mall-order
```

- `mall-seckill` **不直连 market 库的业务表**（活动表除外，见下）；
- 建单走 `mall-order` 新增 gRPC `CreateSeckillOrder`，不复制订单逻辑；
- 库存回补走 `mall-goods` 新增 gRPC `DeductStock` / `ReturnStock`（PRD §5.2 已预留）。

**例外**：`mall-seckill` 读 `seckill_activities` 表（活动元数据、库存上限）。这张表属于营销域，秒杀服务是它的所有者。同理 `seckill_orders` 也归秒杀服务写。

## 3. 数据模型

两张表已存在于 [db-schema.sql](../spec/db-schema.sql)，本节说明语义与约束的使用方式。

### 3.1 seckill_activities（营销域，mall-seckill 所有）

| 列 | 用途 |
|---|---|
| `total_stock` | 活动库存上限，预热时写入 Redis |
| `sold_stock` | **DB 侧兜底计数**，消费者落库时条件更新 |
| `redis_key` | 预热后的库存键名，形如 `seckill:stock:{activity_id}` |
| `status` | 1 草稿 / 2 上线 / 3 结束 |

### 3.2 seckill_orders（mall-seckill 所有）

| 列 | 用途 |
|---|---|
| `voucher_no` | 凭证号 = 预生成的 `order_no`，`uk_voucher` 唯一 |
| `status` | 1 queued / 2 pending_payment / 3 paid / 4 fulfilled / 5 timeout / 6 cancelled |
| `uk_activity_tenant` | **每人限购 1 的最终防线** |

`uk_activity_tenant` 是超卖防线的最后一道：即使 Redis 判重失效、Kafka 重复投递，DB 唯一索引也会拒绝第二次插入。

### 3.3 与 mall_orders 的关系

秒杀订单在 `mall_orders` 里是一条 `kind=3` 的记录，由消费者通过 `mall-order` 创建。

**发现的现有缺陷**：[timeout.go:143](../mall-order/timeout.go) 的 `restockOrder` 对非 kind=1/2 的订单执行：

```sql
UPDATE goods g JOIN mall_order_items i ... SET g.stock = g.stock + i.qty
WHERE i.order_no = ? AND (o.kind = 2 OR g.limited = 1)
```

秒杀库存独立于 `goods.stock`（在 `seckill_activities.sold_stock` + Redis），这条 SQL 会给普通商品库存虚增。**R4 必须同时修复**：`restockOrder` 对 `kind=3` 跳过 `goods.stock` 回补，改由秒杀服务回补 Redis 与 `sold_stock`。

## 4. 抢购链路

### 4.1 请求流程

```
POST /api/v1/seckill/{id}/buy
  │
  ├─ mall-bff：会话鉴权 + 令牌桶限流（超限 MALL_40004）
  │
  ├─ mall-seckill.Buy(activity_id, tenant_id)
  │    ├─ 校验活动状态与时间窗（DB 读，可缓存）→ MALL_40001
  │    ├─ Lua 原子：判重 + 判库存 + DECR → MALL_40002 / MALL_40003
  │    ├─ 预生成 order_no（M + yyyyMMddHHmmss + 6 位随机）
  │    ├─ produce seckill.orders（等 broker 确认）
  │    └─ 返回 202 {voucher, status:"queued"}
  │
  └─ 客户端轮询 GET /seckill/orders/{voucher}
```

**关键约束：produce 成功后才返回 202。** 若先返回再异步发消息，produce 失败会导致"用户以为抢到了、实际没有订单"，且 Redis 已扣的库存无人回补。这里选 at-least-once：produce 失败则回补 Redis 并返回 5xx，客户端重试。

### 4.2 Lua 脚本

```lua
-- KEYS[1] = seckill:stock:{activity_id}     Int 剩余库存
-- KEYS[2] = seckill:buyer:{activity_id}     Set 已抢购的 tenant_id
-- ARGV[1] = tenant_id
-- return {code, remain}
--   code: 1=成功, -1=售罄, -2=重复抢购, -3=库存键缺失
local stock = redis.call('GET', KEYS[1])
if not stock then return {-3, 0} end
stock = tonumber(stock)
if stock <= 0 then return {-1, 0} end
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return {-2, stock} end
redis.call('SADD', KEYS[2], ARGV[1])
redis.call('DECR', KEYS[1])
return {1, stock - 1}
```

用 Set 而非 String 判重，理由：Set 的 `SISMEMBER` 是 O(1)，且天然表达"每人限 1"；活动结束时整键删除即可，不需要逐个清理。

**判重先于判库存**：已抢过的用户即使库存归零也应收到 `MALL_40003`（重复）而不是 `MALL_40002`（售罄），否则用户会误以为活动还没抢完。

### 4.3 Kafka 消息格式

Topic：`seckill.orders`，分区键 = `activity_id`（保证同一活动的消息有序）。

```json
{
  "voucher": "M2026112712345999xyzw",
  "activity_id": 1,
  "tenant_id": 42,
  "goods_id": 113,
  "price_cent": 6900,
  "created_at": "2026-11-27T12:34:59.123Z"
}
```

复用 `pkg/kafka`（`Producer` 单 topic 绑定，`RequireAll` 确认）。

### 4.4 消费者落库

```
FetchMessage → 事务：
  ├─ INSERT seckill_orders(status=2 pending_payment)   ← uk_voucher 幂等
  ├─ UPDATE seckill_activities SET sold_stock = sold_stock + 1
  │    WHERE id = ? AND sold_stock < total_stock        ← DB 兜底，防超卖
  └─ gRPC mall-order.CreateSeckillOrder(voucher, ...)   ← 建 kind=3 订单
CommitMessages
```

**三步必须同事务**（`mall-order` 在同一 market 库，可加入本地事务）。若 `CreateSeckillOrder` 走 gRPC 无法同事务，则改用 outbox：消费者写 `seckill_orders` + `fulfillment_tasks` 同事务，worker 异步建单——与 mall-order 现有 outbox 模式一致。

**裁定：用 outbox。** 理由：跨服务不能共享事务，而 outbox 是仓库既有且已验证的模式（ADR-004）。消费者只负责"把秒杀订单落库"，建单交给 outbox worker。

重复消息的处理：`uk_voucher` 冲突 → 跳过（消息已处理过）；`uk_activity_tenant` 冲突 → 说明 Redis 判重失效，记录告警指标但不回补库存（用户确实抢到了，只是重复投递）。

## 5. 运营侧

### 5.1 活动预热

管理端触发（R6 前用脚本），步骤：

1. 校验 `status=1`（草稿）、`start_at` 在未来；
2. 计算初始库存 = `total_stock - sold_stock`；
3. `SET seckill:stock:{id} {n}`，`DEL seckill:buyer:{id}`；
4. `UPDATE seckill_activities SET status=2, redis_key='seckill:stock:{id}'`。

**预热必须幂等**：重复执行时若键已存在，不覆盖（避免重置已消耗的库存）。用 `SET ... NX`，失败则说明已预热过，只更新 `redis_key` 与 `status`。

### 5.2 活动结束

`status=3`，删除 Redis 键。已产生的订单不受影响（它们已是普通订单）。

### 5.3 时间窗校验

`Buy` 入口校验 `now BETWEEN start_at AND end_at`。**不依赖 Redis 过期**——Redis 键的 TTL 只作为兜底清理，业务判断以 DB 时间为准。

## 6. 超时回补

### 6.1 扫描

秒杀消费者进程内起一个 ticker（60s 一轮，与 mall-order 的 timeout loop 同节奏）：

```sql
SELECT voucher_no, activity_id FROM seckill_orders
WHERE status = 2 AND created_at < NOW() - INTERVAL 15 MINUTE
LIMIT 100
```

### 6.2 回补幂等

```sql
UPDATE seckill_orders SET status = 5
WHERE voucher_no = ? AND status = 2
```

`RowsAffected = 1` 才执行回补：

```
Redis: INCR seckill:stock:{activity_id}
       SREM seckill:buyer:{activity_id} {tenant_id}
DB:    UPDATE seckill_activities SET sold_stock = sold_stock - 1
```

**这是对账口径中唯一的自动回补场景**（D16）。普通订单的超时回补属状态机常规动作，不在此列。

Redis 回补失败时记录差异，由对账 job 兜底——不能因为 Redis 不可用就跳过 DB 回补，也不能只回补一半。

### 6.3 与 mall-order 超时的关系

秒杀订单超时（15 分钟）与普通订单超时（30 分钟）是两条独立扫描。秒杀订单在 `mall_orders` 里也有一条 `kind=3` 记录，会被 mall-order 的 30 分钟扫描看到——**必须在 mall-order 侧跳过 kind=3**，否则会双重关闭 + 库存虚增。

这是 §3.3 提到的 `restockOrder` 缺陷的完整修复范围。

## 7. 对账

### 7.1 口径

```
Redis 余量 + 已售出（DB sold_stock） == total_stock
```

不一致即记录差异。**默认保留待核查，不自动回滚**（沿用 reconciler 的 `-no-auto-reverse` 口径，D16）。

### 7.2 差异分类

| 现象 | 可能原因 | 处置 |
|---|---|---|
| Redis 余量 < DB 期望 | 有扣减未落库（消费者停） | 保留，等消费者恢复 |
| Redis 余量 > DB 期望 | 回补重复 / 扣减丢失 | 保留，人工核查 |
| `sold_stock` > `total_stock` | 超卖（不应发生） | 告警 + 人工介入 |

### 7.3 执行形态

独立子命令 `mall-seckill reconcile`（不常驻），由 cron / 手动触发。这与 billing reconciler 的形态一致。

## 8. API 契约

严格遵循 [api-contract §6](../spec/api-contract.md)，不新增端点。补充实现细节：

| 端点 | 说明 |
|---|---|
| `GET /seckill/activities` | 列表；`remain` 从 Redis 读，键缺失时回退 DB 计算 |
| `POST /seckill/{id}/buy` | 202 + voucher；错误码 MALL_40001~40004 |
| `GET /seckill/orders/{voucher}` | 轮询；status 映射见下 |

**凭证查询的越权防护**：`GET /seckill/orders/{voucher}` 必须校验 `tenant_id` 匹配，否则任何人猜到 voucher 就能看到别人的订单状态。voucher 含 6 位随机，但不是安全边界。

**状态映射**：

| DB status | API status |
|---|---|
| 1 queued | `queued` |
| 2 pending_payment | `pending_payment` |
| 3 paid | `paid` |
| 4 fulfilled | `fulfilled` |
| 5 timeout | `timeout` |
| 6 cancelled | `cancelled` |

## 9. 限流

秒杀入口令牌桶（api-contract §8 第二层），实现于 mall-bff：

- 键 `seckill:rate:{tenant_id}`，`INCR` + `EXPIRE` 60s；
- 阈值待压测定容（初始 10 次/分钟）；
- 超限返回 `MALL_40004`（429，`retryable: true`）。

注意与基础限流（120 req/min）叠加：秒杀入口的桶更紧，两层都过才放行。

## 10. 压测方案

### 10.1 场景

| 场景 | 目的 | 指标 |
|---|---|---|
| 预热 100 件 → **10000 并发抢** | 验证不超卖 | Redis 余量=0、DB 订单=100、零唯一索引冲突 |
| 同一租户连抢 10 次 | 验证限购 | 恰 1 单成功，9 次 MALL_40003 |
| 持续 10 分钟中低并发 | 验证稳定性 | P99、错误率、内存 |
| 停消费者后抢购 | 造滞留 | 对账 job 检出差异 |

### 10.2 工具

沿用仓库既有 `tools/` 下的压测脚手架（vegeta 或自研 Go 客户端）。报告落 `docs/plans/` 或 `docs/`。

**压测客户端必须用连接复用**（Go 的 `http.Transport` 复用 keep-alive，或 vegeta 的默认行为）。若每个请求新建 TCP 连接，10000 并发会瞬间耗尽本机临时端口——macOS 的 `net.inet.ip.portrange` 是 49152–65535，约 1.6 万个可用端口，扣掉 TIME_WAIT 后连两轮都跑不完。

### 10.3 本地环境约束（10000 并发）

本机 macOS 的实测限制，压测前必须确认：

| 项 | 当前值 | 说明 |
|---|---|---|
| `ulimit -n` | 1048576 | 文件描述符充足 |
| `kern.ipc.somaxconn` | 128 | **accept 队列上限**；10000 并发同时建连会丢 SYN |
| `net.inet.ip.portrange` | 49152–65535 | 约 1.6 万临时端口 |
| `net.inet.tcp.msl` | 15000 ms | TIME_WAIT 持续 30s（2×MSL） |

**结论：10000 并发在本机可跑，但必须满足两个前提**——

1. **客户端复用连接**（见 10.2）。连接数 = 并发数时才吃端口；复用后 10000 并发可能只需要几百个连接。
2. **服务端 accept 队列调大**：`sudo sysctl -w kern.ipc.somaxconn=1024`（重启失效）。不调的话，瞬时建连会被内核丢 SYN，表现为客户端看到随机超时——**这会污染压测结论，不能归因于业务代码**。

若本机仍跑不动，允许降级为「10000 请求总量、1000 并发」并在报告中明确写出实际参数。**不允许**悄悄调小并发后声称通过 10000 并发验收。

### 10.4 判定

- 超卖：`SELECT SUM(sold_stock) FROM seckill_activities` 与 `SELECT COUNT(*) FROM seckill_orders WHERE status != 5` 必须相等且 ≤ total_stock；
- 一致性：`GET /seckill/activities` 的 `remain` = 0；
- 错误率：抢购成功的请求零 5xx（限流 429 不计入错误）。
