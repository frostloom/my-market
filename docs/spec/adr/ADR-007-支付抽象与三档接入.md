# ADR-007 支付抽象与三档接入

- 状态：已接受（对应 PRD D10 / §5.5）
- 日期：2026-11-17（2026-11-18 审核补回调图后固化）

## 背景

个人无法取得微信/支付宝商户资质（需企业/个体工商户）。AI 充值侧的支付要求"最终接入真实"，普通商品维持模拟。

## 决策

- `PaymentProvider` 接口：CreatePayment / HandleCallback / QueryPayment；现实现 `MockPaymentProvider`；
- 状态机从第一天按真实支付语义：下单≠支付≠入账、异步回调驱动、验签占位、payment_records 流水、幂等与对账；
- 三档接入路径：档一 mock（现在）→ 档二 Stripe test / PayPal sandbox（个人可注册，真实回调假钱，演示级）→ 档三 个体工商户资质后接微信支付 Native / 支付宝当面付（最终形态）。切换只换 Provider。

## 理由

- 商户资质是政策约束而非技术约束，架构不应被其锁死；
- 档二让"完整支付回调链路"可演示而不涉真钱与合规风险（对外收款涉 ICP/生成式 AI 备案）。

## 后果

- 所有金额校验以回调为准（create 时只建流水）；验签在档一为占位实现，档二起为真实验签；
- R2 验收含"重复回调幂等"用例。

## 更新（2026-11-22：建单步骤落位与接口收窄）

2026-11-21 审查发现 PRD §5.2 明文的「CreatePayment（写 payment_records=created）」一直未实现（在途支付单防线缺失，同订单并发 /pay 可拉起多笔渠道支付）。修复后接口分两半：

- **建单半边在 mall-order**：新 gRPC `BeginPayment`（OrderService）在订单行锁内「复用在途单或新建 payment_records=created 并分配 trade_no」——单号生成从 Provider 移入订单域，保证同订单任何时刻至多一张在途单；金额防御校验（>0）同侧兜底，错额拒付口径不变（仍以回调为准）。
- **渠道半边才是 Provider**：bff 侧 PayProvider 收窄为回调排程（现仅 ScheduleCallback）；档二真实渠道接入时在此扩 CreatePayment（拿 BeginPayment 分配的单号去渠道建单）。mall-order 的旧 PaymentProvider/CreatePayment 成为未接线的历史抽象，收编删除随档二一并裁定。

本更新不改变三档路径与「切换只换 Provider」的承诺；单渠道部署（档一/档二）下在途单复用不区分 provider——防双扣款优先于跨渠道单号语义。
