## 决策（B+ 全文）

ai-gateway 目录消失，十个服务平铺 `services/`，商城与 AI 域同构：

```
services/{gateway, billing, router, agent, mock-provider, mall-bff, mall-goods, mall-order, seckill, mall-gen}
```

1. **全仓单模块** `github.com/frostloom/my-market`：删除第二个 `go.mod`（`github.com/frostloom/ai-gateway`）、`go.sum`、`go.work` 与根模块 replace；全部 import 路径一次性改写进单模块。评测工具迁 `tools/`（13 个 cmd + internal 基建），冻结证据校验器迁 `tools/verify/`（r26-canonical 垫片保字节链），共享库归 `pkg/`（jev/observability/supportconfig/upstream/gatewayclient 为裁定 B 追加；kafka/quota/xid/trace 按确认清单留 pkg，裁定 C1）。
2. **billing 域归并三进程**：`services/billing/cmd/{billing,reconciler,event-consumer}` 三进程共享一份 `internal/` 与 `store` 数据层；`ai_gateway` 库的 DDL（`schema.sql`）随迁 `services/billing/scripts/`（裁定 E1）——**库的 owner 是 billing**。
3. **边界 = 编译器 + 白名单门禁双层**（下节）：服务 `internal/**` 由 Go 编译器强制；树内非 internal 的「公开位」与 mall 域越树 import 由改造版 `pkg/importguard` 白名单门禁强制。
4. **行为零变化**：80/81 基线失败名集合恒等、四冒烟与冻结证据校验链全绿背书。

## 四条底线对照

（R2.7 计划 Goal 立的四条底线；①②为计划明示编号）

| 底线 | B+ 落法 | 证据位 |
|---|---|---|
| ① 服务边界由编译器强制 | 单模块下每服务一份 `internal/`，树外 import 编译失败；恶意导入实证见下节 | `services/*/internal/`；`go build` 实证 |
| ② 数据所有权显性化 | reconciler/event-consumer 声明为 billing 域工人（三进程一份 internal，见「数据所有权」节）；schema.sql 归位 billing 树 | `services/billing/`；裁定 E1 |
| ③ 结构同构 | ai-gateway 目录消失，七服务平铺与商城 `services/mall-*` 同构；cmd/internal/store 层级一致 | `services/` 十目录 |
| ④ 依赖方向显性治理 | 跨树依赖全部进入白名单口径（公开面四位置、合法户三+一），无隐性伸手；门禁测试把口径固化为可执行规格 | `pkg/importguard` 哨兵表 |

## 边界治理：编译器管 internal，门禁管公开面

单模块把「跨服务 import」从 workspace 边界问题变成包可见性问题。Go 的 `internal/` 规则天然强制一层（树外 import 直接编译失败），但 A-i 裁定把四个跨域包放在服务树**非 internal** 目录（包源码零改动，编译可过），这些「公开位」编译器管不到——由 `pkg/importguard`（改造版，未删除）以静态扫描门禁治理：

- **规则 0（退役路径）**：`github.com/frostloom/ai-gateway/**` 复活即拒（独立模块已合并退役）。
- **规则 1（mall 域隔离）**：`services/mall-*` 禁止 import `services/{billing,gateway,router,agent,mock-provider}/**`；mall 对 AI 域唯一合法契约面 = `pkg/proto/billing/v1`（R2 以来 allowedPrefix 语义保留）。
- **规则 2（公开面白名单）**：四个公开位按名单治理，同树 import 恒合法，其余一律拒绝：

| 公开位 | 跨树合法户 |
|---|---|
| `services/billing/store`（+子包） | `services/agent/**`（生产码）、`tools/**`（评测基建）、`services/billing/internal/channelintegration` |
| `services/billing/admin` | 同上三户 |
| `services/router/router`（公开面同法） | 同上三户 |
| `services/agent/agent` | `tools/**` |

规格以测试表固化（TDD）：`pkg/importguard/boundary_test.go` 哨兵表 26 用例（正向白名单户 / 反向越界形态），守卫自检 = 扫描面每根 >0 文件 + 合成哨兵（同一「解析→规则」管线对恶意源码必须报违规）。

### 恶意导入双实证（T3，2026-11-20）

完整命令与输出存档于 `docs/plans/sdd-archive-R2.7/R2.7-ledger.md（含 T3 实证节）`：

1. **编译器层（底线①）**：mall-order 临时文件 import `services/billing/internal/server` → `CGO_ENABLED=0 go build ./services/mall-order/` → `use of internal package … not allowed`（exit 1）。
2. **门禁层**：同文件改 import `services/billing/store`（公开位，编译器放行，`go build` exit 0）→ `go test ./pkg/importguard/` → `FAIL: TestImportBoundary_RepoScanGreen … import "…/services/billing/store" 越界: mall 域禁止 import AI 服务树 services/billing/`（exit 1）。

两段证据合起来证明：internal 越界编译期即红；公开位越界编译器不红、门禁红——双层无缝。

### agent 直读 store：已存在的跨域债（如实入档）

`services/agent/agent`（现金工具/客服运行时）生产 import `services/billing/store` 是**拆分前就存在的跨域依赖**（R2 时代 agent 直读 billing 数据层，见映射 §3.1-1）。本决策不追认其为理想态，只如实入档：

- 现状：白名单放行（`services/agent/**` 在 store/admin/router 三公开位的合法户名单内），不阻塞拆分；
- **后续项（未排期）**：agent→billing 改走 gRPC 契约（API 化），消除对 billing 数据层的直读；届时白名单三户收窄为 {tools, channelintegration}；
- 在此之前，任何**新增**的 agent 直读面扩散（如伸手 billing `internal/**`）依然被编译器拒绝。

## 数据所有权声明：reconciler / event-consumer = billing 域工人

`ai_gateway` 库（ bills/topups/tenants 等）的唯一 owner 是 **billing 域**。`cmd/reconciler`（滞留账单对账）与 `cmd/event-consumer`（计费明细消费落账）不是独立服务，而是 **billing 域的两个后台工人进程**——与 `cmd/billing` 共享 `services/billing/internal/` 与 store 数据层，三进程一份代码。由此推论：

- 这两个进程的表访问、迁移（`services/billing/scripts/schema.sql`）、对账口径都归 billing 域治理，不设跨域数据接口；
- mall 域对账（R4 秒杀/订单对账 job）只碰 `market` 库，与 `ai_gateway` 库无交集；
- 未来若工人独立成部署单元，代码仍属 billing 树（进程拓扑变化不动所有权）。

## importguard 沿革：从「退役」到「改造」（退役理由的演变）

- **R2（双模块时代）**：守卫只管「mall→ai-gateway 仅许 `pkg/proto/billing/v1`」一条规则（parser 静态扫描 + replace 边界 + Dockerfile 四层防线）。
- **R2.7 原计划**：单模块后「importguard 删除、编译器全接管」——删除理由：旧守卫的管辖对象（跨模块 import）已随模块合并消失。
- **裁定 A 修订（本决策）**：A-i 公开位方案下编译器存在盲区（四个非 internal 跨域包），守卫不退役、改造为**白名单门禁**：管辖对象从「模块边界」升级为「服务边界」——规则 0/1/2 见上节。原 allowedPrefix 语义作为规则 1 的契约面保留。
- `pkg/importguard` 因此保留在结构清单（计划 Global Constraints 中「importguard 退役」一行由本 ADR 取代）。

## 先例：Kubernetes 的单模块治理

大型单仓不等于边界失控：Kubernetes 以**单 Go 模块**承载数千个包与多个逻辑组件，跨组依赖由目录边界（`internal/` 编译器规则 + `pkg/` 公开面纪律 + hack/verify 脚本门禁）治理，而非模块切分。B+ 在本仓规模复用同一机制组合：编译器管 internal（免费、零误报），白名单门禁管公开面（本仓特有的 A-i 需求），ADR 把口径写成文字。模块切分（独立 go.mod）留作 R3+ 服务真正独立部署/独立版本化时的演进项，届时公开位 API 化（含 agent→store 后续项）是前置条件。

## 后果

**正面**：

- mall 与 AI 域的物理耦合面收敛到一个 proto 契约目录；越界从「运行时才发现」提前到「编译/测试期即红」；
- 数据所有权从口头约定变成目录事实（billing 三工人 + schema.sql 同树）；
- 边界规则有可执行的规格（哨兵表）与双实证，不靠自觉。

**代价与残留（如实入档）**：

- `pkg/` 公开面（jev/observability/gatewayclient 等）对 mall 同样可见，门禁规则未覆盖 pkg 树（mall 当前零 import，风险为理论性）；若未来出现伸手，先入 ADR 白名单或扩展规则 1；
- agent 直读 store 为存量跨域债，API 化列后续项（见上）；
- `docs/ai-gateway/` 冻结历史文档存在 117 条死链（迁移与历史债所致），处置口径见该目录置顶说明，不做全量回改；
- 单模块意味着一次 `go build ./...` 构建全部服务——CI 以分域 GOTEST_TARGET 与基线棘轮补偿（mall job / ai-gateway job 各管各域包面）。
