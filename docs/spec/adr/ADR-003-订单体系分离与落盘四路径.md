# ADR-003 订单体系分离与落盘四路径

- 状态：已接受（对应 PRD D4/D11；v0.3 修正机制归属）
- 日期：2026-11-17（2026-11-18 修订）

## 背景

billing 已有充值订单（RechargeOrder）与推理账单（bills）。商城是否收编充值订单？曾以"持久化机制不同"为分离理由，经代码核查证实该理由表述有误。

## 事实修正（关键）

- 充值 topups：**同步 MySQL 事务**（topup 行 + tenants.ledger_balance 同事务，MySQL 为权威与提交点，Redis 是事后投影）；
- 推理 bills：Redis 实时余额权威 + `BILLING_LEDGER_BATCH_SECONDS` 定时批量刷 MySQL；
- 两条链路机制不同，均成熟且**不动**。

## 决策

mall_order 为 market 库独立订单体系；四条落盘路径并存：推理 bills 批量异步（既有）/ 充值 topups 同步事务（既有）/ mall_order 支付同步事务+outbox 履约（新）/ seckill Kafka 异步（新）。**分离理由 = 业务域与演进隔离**，非持久化机制差异。portal 老收银台（现 403 关闭）是否收编为 P2 待决策。

## 理由

- 动 RechargeOrder/PayRecharge（有单测覆盖的计费核心路径）风险大收益小；
- 商城订单语义（购物车/混合行/秒杀）与充值语义差异大，强行同表互相污染；
- 两套账最终收敛于 topups 的 ref 幂等入账，账不分家。

## 后果

- 面试话术："portal 收银台是自助遗留路径，商城是统一售卖入口，收编在演进路线"；
- 需维护两套状态机（各自域内）。
